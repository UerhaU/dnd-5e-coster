Уточнения объёма: первая стабильная версия поддерживает одну изменяющую комнату на кампанию и конструктор 1-го уровня. Несколько кампаний и партий сохраняются. Одновременные комнаты одной кампании, мультиклассирование и офлайн-слияние требуют отдельных этапов. Это ограничения первой версии, а не удаление дальнейших возможностей.

Резервирование и восстановление перенесены перед массовым развитием контента: это условия сохранности рабочей кампании. Полный экспорт/импорт для переноса, 3D и свободная компоновка панелей остаются следующими возможностями.

## Основания в текущем проекте

Проверены исходники и сохранённые отчёты, без запуска приложения и изменения базы:

- `backend/src/app.ts`: WebSocket принимает `userId` из query, несколько изменяющих API принимают `masterUserId`/`userId` из тела. Проверки мастерства по такому ID не равны проверенной сессии.
- `/api/bootstrap` в том же файле выбирает общий список пользователей, кампаний, персонажей и состояний; в показанном обработчике нет фильтра по аутентифицированному владельцу.
- Откат заклинания восстанавливает прежний `sheetJson`, передачи — прежние JSON-инвентари. Это конкретное основание требовать компенсацию и контроль последующих изменений.
- `prisma/schema.prisma`: есть разделение библиотечного и кампанийного состояния, глобальный хоумбрю и связи с кампаниями. В текущем `ImportedContent` нет отдельного хранилища исторических ревизий пакетов; источник связан одной основной ссылкой.
- `src/realtime.ts`: уже используется WebSocket и `room:refreshed`; новый транспорт для исправления семантики не нужен.
- `package.json`: React/Vite, Fastify, Prisma/SQLite уже выбраны. Отдельных зависимостей и команд Vitest/Playwright пока нет.
- Отчёт импорта от 2026-06-01: 4584 записи, 109 без сопоставленного источника, 210 с неизвестной редакцией. Это исторические данные отчёта, не повторный подсчёт текущей базы.
- План этапа 5 фиксирует прежние пользовательские настройки всех DLC и простого списка источников. Изменение новых значений по умолчанию описано явно; простой список сохранён, технические статусы не навязываются постоянными метками.

Это перечень наблюдений для приоритизации, не полный аудит безопасности или корректности всех маршрутов. Новые требования не считаются исправленными в коде после правки документа.

## Следующая разработка

Последующее решение пользователя 2026-10-15 заменяет первоначальный приоритет инфраструктуры: сначала закончить основной функционал и внешний вид локально, затем заниматься серверной сетевой частью и защитой. Публикация не требуется.

Порядок: A — локальный персонаж и лист; B — локальные игровые функции; C — законченный интерфейс; D — LAN, сессии, права, защита и переподключение; E — развитие и дополнительные возможности. Интерфейс делается с каждой функцией A–B и согласуется на C. Используется текущий локальный backend с SQLite, без отдельного инфраструктурного этапа перед функционалом.

Первым нужен небольшой план A: поддержанный набор пакетов 1-го уровня → создание героя → объяснимый лист → сохранение и повторное открытие → проверка интерфейса и сценария. Локальные тестовые роли допустимы. Сохранность данных, верные расчёты и безопасная отмена входят в качество локальных функций и не переносятся целиком на сетевой этап. Рабочую базу не использовать для тестов.
