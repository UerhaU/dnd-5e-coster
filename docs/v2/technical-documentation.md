## 0. Как пользоваться документом

- **Решение принято** — записано в разделе 2 с датой. Меняется только новой записью с причиной, старая не стирается, а помечается «заменено».

## 1. Цель и границы

**Портативное десктопное приложение для Windows** для игры в D&D 5e (редакция 2014) на русском языке. Одна и та же программа работает в двух режимах:

- **мастер (хост)** создаёт игру: его приложение хранит кампанию и принимает подключения;
- **игрок (клиент)** подключается к мастеру по адресу или коду.

Подключиться можно в домашней сети и через интернет (раздел 4.5). Создание и хранение своих персонажей работает и без подключения.

Проект домашний и некоммерческий. Нет ни публичного сайта, ни облачного сервиса, ни центрального сервера разработчика.

**Ориентиры:**

- **Правила и числа** — D&D 5e 2014 по данным DnD.su.
- **Интерфейс и подача** — Baldur's Gate 3: порядок создания персонажа, инвентарь, кукла с надетым снаряжением, подсказки с разбором расчёта (раздел 8.2).

**Первая цель v2** — каталог объектов D&D и создание персонажа с функционалом из макетов Figma. Кампании, игровые комнаты и сеть строятся на следующих этапах (раздел 11).

Вне рамок до отдельного решения: macOS и Linux, карта и миниатюры, 3D, мобильные приложения, игроки через браузер.

## 4. Архитектура

### 4.1. Общая схема

```
┌──────────── Приложение мастера (режим «Хост») ────────────┐
│  Окно (React) ──IPC/HTTP──▶ Встроенный сервер (Fastify)   │
│                                 │        │                │
│                         catalog.db    data/user.db        │
│                                 ▲                         │
└─────────────────────────────────┼─────────────────────────┘
                     HTTP + WebSocket (LAN или виртуальная сеть)
┌─────────────────────────────────┼─────────────────────────┐
│  Окно (React) ──────────────────┘                         │
│  Приложение игрока (режим «Клиент»)                       │
│  своя catalog.db и data/user.db — библиотека персонажей   │
└───────────────────────────────────────────────────────────┘
```

Как это работает:

- В Electron есть **главный процесс** (Node.js: файлы, база, сеть) и **окно** (интерфейс React).
- Главный процесс **всегда** запускает встроенный сервер на `127.0.0.1`. Интерфейс работает с ним даже без игры: каталог, персонажи, хоумбрю.
- Когда мастер нажимает «Открыть игру», сервер начинает слушать и сетевой адрес, чтобы к нему могли подключиться игроки. Закрыл игру — доступ извне снова закрыт.
- Игрок в режиме «Подключиться» работает со своим локальным сервером, а данными игры обменивается с хостом мастера.
- **Авторитетные данные кампании хранятся только у мастера** (ТЗ, раздел 3.3). Приложение игрока показывает разрешённую ему часть и отправляет команды.
- Персонажи игрока лежат в его `user.db`. При входе в кампанию копия персонажа передаётся мастеру и дальше живёт в кампании (ТЗ, раздел 3.2).

### 4.2. Портативность

Состав zip-архива:

```
Koster/
├─ Koster.exe
├─ resources/          код программы и catalog.db (меняются при обновлении)
├─ data/               создаётся при первом запуске, сохраняется при обновлении
│  ├─ user.db          персонажи, кампании, хоумбрю, настройки
│  ├─ backups/
│  ├─ portraits/       загруженные картинки
│  ├─ logs/
│  └─ electron/        служебные файлы Electron и кэш Chromium (Р43)
└─ README.txt
```

Правила:

- Программа ничего не пишет в `AppData`, реестр и системные папки. Все пути считаются от папки программы. В Electron для этого при запуске перенастраиваются служебные пути (`app.setPath('userData', …)`), иначе Electron сам кладёт кэш в `AppData`.
- Обновление: заменить всё, кроме `data/`. Перед миграцией `user.db` программа сама делает бэкап.
- Если папку нельзя изменять (например, она лежит в `Program Files`), программа показывает понятную ошибку, а не тихо пишет в другое место.
- Сборка: `electron-builder`, цель `zip` (папка программы). Однофайловый «portable exe» не используется: он при каждом запуске распаковывается во временную папку и запускается медленно.
- Релизы публикуются в GitHub Releases этого репозитория.

### 4.3. Структура репозитория

npm workspaces, один `package.json` в корне:

```
/
├─ apps/
│  └─ desktop/        Electron: главный процесс, preload, окно
├─ packages/
│  ├─ ui/             интерфейс: React, экраны, компоненты, дизайн-токены
│  ├─ server/         встроенный сервер: Fastify, маршруты, WebSocket
│  ├─ db/             схемы Drizzle, миграции, доступ к catalog.db и user.db
│  ├─ shared/         общие типы и схемы Zod (API, команды, объекты)
│  ├─ rules/          движок правил: чистые функции без React, сервера и базы
│  └─ importer/       импорт DnD.su и сборка catalog.db (только для разработки)
├─ data/
│  ├─ reviewed/       проверенные вручную правила и исправления (в git)
│  └─ fixtures/       сохранённые страницы для тестов (в git)
├─ design/            ссылки на Figma, функциональные схемы, концепции стиля, решения по дизайну
├─ storage/           кэш страниц и рабочие базы разработчика (не в git)
├─ docs/
└─ scripts/
```

Правила размещения:

- Код, нужный и интерфейсу, и серверу, лежит только в `packages/shared` или `packages/rules`. Копий нет.
- `packages/rules` ничего не знает о базе, сети и React: на вход данные, на выход результат.
- Импортёр не входит в собранную программу. Он собирает `catalog.db` на компьютере разработчика, а готовый файл попадает в релиз.
- Один файл — одна ответственность. Ориентир — до ~300 строк, файл больше 500 строк — повод разделить.

### 4.4. Стек

| Область | Инструмент | Комментарий |
| --- | --- | --- |
| Язык | TypeScript (strict) | Скрипты тоже на TS |
| Десктоп | Electron + electron-builder | Сборка в zip-папку для Windows x64 |
| Интерфейс | React 19, Vite, React Router | Через `electron-vite` для разработки и сборки |

### 4.5. Сеть и безопасность

**Подключение.**

- Мастер нажимает «Открыть игру» в своей кампании, выбирает порт (по умолчанию, например, 47800) и видит адреса для подключения: в домашней сети и в виртуальной сети, если она есть.
- Мастер копирует **приглашение** одним нажатием: строку с адресом, портом и кодом комнаты (Р30). Игрок вставляет её в одно поле «Подключиться».
- В домашней сети программа игрока сама находит открытые игры и показывает их список (UDP-рассылка в локальной сети). Через интернет автопоиск не работает, там нужно приглашение.
- Через интернет рекомендуемый путь — виртуальная сеть (Р25). Тогда для приложения игроки как будто сидят в одной домашней сети. В документации к программе будет пошаговая инструкция для выбранного сервиса.
- Проброс порта на роутере допустим, но это на ответственности мастера. Программа об этом предупреждает.
- При первом открытии игры Windows спросит разрешение брандмауэра. Программа заранее объясняет, что нажать.

**Защита (Р19).**

- Общего входа при запуске программы нет (Р31). Вход нужен только в чужую кампанию: по учётной записи игрока (имя и пароль, заданные в этой кампании) и коду комнаты.
- Учётная запись создаётся при первом подключении к кампании, мастер подтверждает нового участника. При создании игрок получает код восстановления.
- Забытый пароль сбрасывает мастер в списке участников кампании либо игрок вводит код восстановления. Почта и внешний сервер не используются.
- Пароли и коды восстановления хранятся только в виде хеша. После входа сервер выдаёт токен сессии, и тот проверяется на каждом HTTP-запросе и WebSocket-подключении.
- Личность пользователя код получает в одном месте — `getCurrentUser(request)`. Обработчики не берут `userId` из тела запроса.
- Права проверяет сервер: игрок меняет только своего персонажа и видит только разрешённые данные (ТЗ, раздел 4).
- Ограничение частоты попыток входа, лимиты на размер запросов и загружаемых файлов.
- Тексты с DnD.su и хоумбрю показываются как текст, без вставки чужого HTML.
- Окно Electron изолировано от Node.js (`contextIsolation`, `sandbox`, без `nodeIntegration`). Интерфейс общается с главным процессом только через узкий набор функций в preload.
- Режим разработки с открытыми тестовыми профилями включается только явно и в собранной программе выключен.

**Согласованность.** Изменения игры выполняются командами с `requestId`, ожидаемыми версиями и одной транзакцией на команду (ТЗ, раздел 18). Обрыв связи не теряет и не дублирует действие; после переподключения клиент запрашивает актуальное состояние.

**Версии.** Клиент и хост сверяют версию протокола и каталога при подключении. Если они несовместимы, игрок видит понятное сообщение, что нужно обновить программу.

## 5. Модель данных

### 5.1. Каталог (`catalog.db`): главная идея

В v0.1 почти каждое понятие D&D получило свою таблицу: 103 таблицы только для заклинаний, снаряжения и рас. В v2 используется **гибридная схема**:

1. **Общая таблица объектов** для всех категорий: ID, категория, названия, источник, редакция, статус проверки.
2. **Поля для поиска и фильтров** — обычные колонки или небольшие таблицы по категориям (уровень заклинания, школа, CR моба, редкость предмета).
3. **Подробности и механика** — JSON с версией схемы, который при записи проверяется Zod.
4. **Справочники** — небольшие таблицы: источники, школы магии, типы урона, характеристики, состояния, размеры, слоты снаряжения.

Новая категория объектов добавляется схемой Zod и парсером, а не десятком таблиц.

### 5.2. Таблицы каталога (черновик)

| Таблица | Назначение | Ключевые поля |
| --- | --- | --- |
| `sources` | Источники, как их называет DnD.su (Р12). Один источник — одна строка: в v0.1 «Котёл Таши», «Занатар» и «Книга игрока» записаны дважды | `id`, `code`, `name_ru`, `name_en`, `dndsu_source_id`, `edition` |
| `content_entities` | Один объект D&D | `id` (`spell:fireball`, Р11), `category`, `name_ru`, `name_en`, `aliases`, `edition`, `current_revision_id`, `review_status`, `automation` |
| `content_revisions` | Версии объекта. Только добавляются, никогда не меняются и не удаляются (Р21) | `id`, `entity_id`, `revision`, `schema_version`, `data_json`, `rules_json`, `importer_version` |
| `entity_sources` | Объект может быть в нескольких источниках | `entity_id`, `source_id`, `dndsu_id`, `url` |
| `spell_index`, `item_index`, `monster_index`, … | Поля для фильтров | Например, для заклинаний: `level`, `school_id`, `ritual`, `concentration`, классы |
| `content_links` | Связи между объектами | `from_id`, `to_id`, `kind` (`material_component`, `grants_spell`, `variant_of`, …) |
| Справочники | `magic_schools`, `damage_types`, `abilities`, `conditions`, `equipment_slots`, … | `id` (код), `name_ru`, `name_en` |
| `content_search` | Индекс FTS5 | Строится при сборке каталога |
| `catalog_info` | Версия каталога и дата сборки | Сверяется при подключении игрока |
| `spell_index_classes` | Классы заклинания | `entity_id`, `class_code`, `access` (`standard` или `optional` — особый доступ из TCE) |
| Служебные поля | `content_entities.withdrawn` — объект пропал с сайта, ревизии сохранены; `content_revisions.content_hash`, `created_at` | Хеш — SHA-256 канонического JSON: по нему сборка решает, нужна ли новая ревизия |
| Журнал ревизий (Р51) | Файл в git, без текстов | ID объекта, номер ревизии, хеш, дата |

Таблица `conditions` (состояния) добавлена к справочникам на этапе 1: на неё ссылаются проверенные правила заклинаний.

### 5.3. Данные пользователя (`user.db`)

Черновик по мотивам `prisma/schema.prisma` из v0.1, уточняется на этапах 4–5:

- `characters` — библиотека персонажей: сборка (выборы игрока по каждому уровню и ссылки на ревизии каталога), портрет и данные для отображения. Черновик помечается статусом `draft`.
- `character_campaign_copies` — у игрока: копии версий персонажа для кампаний, только для просмотра (Р34), с историей прежних версий.
- `portraits` — исходная картинка, размещение снаряжения по типам изображений, размещение эмоций, итоговый пиксельный портрет 128×128 (Р38–Р40). Файлы лежат в `data/portraits/`.
- `campaigns`, `campaign_members`, `campaign_characters` — у мастера: кампания, участники с хешами паролей и кодов восстановления, главный экземпляр версий персонажей в кампании, текущее настроение персонажа (Р39).
- `campaign_snapshots` — у мастера: контрольные точки кампании (Р32) — ручные, автоматические, «оригинал». Каждая точка хранит согласованное состояние кампании, версию схемы и ссылки на ревизии каталога.
- `homebrew_entities` — хоумбрю в том же формате, что и каталог (ID вида `homebrew:<uuid>`).
- `action_log`, `command_results` — журнал и результаты команд для повторов по `requestId`.
- `settings` — настройки программы.

Ссылки из `user.db` на каталог — пары «ID объекта + номер ревизии». Код проверяет их при записи. Если программа обновилась, а у персонажа ссылка на ревизию, которой нет в новом каталоге (такого быть не должно, но на всякий случай), персонаж открывается в ручном режиме с предупреждением.

### 5.4. Статусы объекта

- `review_status`: `raw` → `parsed` → `reviewed` (проверено человеком) → `rules_verified` (механика проверена контрольным сценарием).
- `automation`: `full`, `assisted`, `display_only`, как в ТЗ.

### 5.5. Пример: заклинание

```jsonc
// content_entities
{ "id": "spell:fireball", "category": "spell", "name_ru": "Огненный шар", "name_en": "Fireball",
  "edition": "5e_2014", "review_status": "reviewed", "automation": "assisted" }

// content_revisions.data_json (схема spell/v1)
{
  "schemaVersion": "spell/v1",
  "level": 3, "school": "evocation",
  "castingTime": { "amount": 1, "unit": "action" },
  "range": { "kind": "distance", "feet": 150 },
  "area": { "shape": "sphere", "radiusFeet": 20 },
  "components": { "verbal": true, "somatic": true,
                  "material": { "text": "…", "itemIds": ["item:bat-guano", "item:sulfur"], "consumed": false } },
  "duration": { "kind": "instantaneous" },
  "concentration": false, "ritual": false,
  "classes": ["class:sorcerer", "class:wizard"],
  "description": [ { "type": "paragraph", "text": "…" } ],
  "higherLevels": [ { "type": "paragraph", "text": "…" } ]
}

// content_revisions.rules_json — механика по модели контента (character-rules/v1)
{ "effects": [ { "type": "damage", "dice": "8d6", "damageType": "fire",
                 "save": { "ability": "dex", "onSuccess": "half" },
                 "scaling": { "perSlotAbove": 3, "dice": "1d6" } } ] }
```

Устройство `rules_json` описано в [универсальной модели контента](../archive/v0.1/character-content-extension-model.md). Для заклинаний действует схема `spell-rules/v1` (Р49).

### 5.6. Миграции и бэкапы

- Структура `user.db` меняется только миграциями Drizzle. Они хранятся в git и применяются при запуске программы.
- Перед миграцией программа делает бэкап в `data/backups/` (через `VACUUM INTO`).
- `catalog.db` не мигрирует: при обновлении программы файл просто заменяется новым.
- Тесты работают только с временными базами.

## 6. Импорт с DnD.su и сборка каталога

Импорт — инструмент разработчика. Пользователь программы получает готовый `catalog.db` в составе релиза.

```
1. fetch      скачать страницы → кэш в storage/ (Р50; только отсутствующие или по явному запросу)
2. parse      HTML → сырые поля
3. normalize  сырые поля → data_json по схеме категории
4. review     наложить ручные исправления из data/reviewed/
5. validate   проверить схемы Zod и связи
6. build      собрать catalog.db; новые ревизии — только для изменившихся объектов
7. report     отчёт: новые, изменённые, пропущенные, ошибочные
```

Правила:

- **Фильтр редакции (Р12):** берутся 5e 2014 и общие для 2014 и 2024. Записи только для 2024 пропускаются и попадают в отчёт. Записи с неизвестной редакцией получают `edition: unknown` и ждут решения.
- **Бережно к сайту:** 1–2 запроса в секунду, повтор с паузой, кэш на диске. Кэш v0.1 используется сразу.
- **Повторный запуск не создаёт дублей.** Старые ревизии переносятся в новую сборку без изменений (Р21).
- **Ошибка одной страницы не останавливает импорт** и попадает в отчёт.
- **Ручные исправления** лежат в `data/reviewed/` и не затираются.
- Каждый парсер покрыт тестами на страницах из `data/fixtures/`.

Порядок категорий подстроен под создание персонажа:

1. Заклинания
2. Снаряжение: оружие, доспехи, щиты, предметы
3. Расы и подрасы
4. Классы, подклассы, предыстории, черты, языки, навыки, инструменты
5. Состояния и справочники
6. Магические предметы
7. Бестиарий

## 7. Встроенный сервер (API)

REST и WebSocket под `/api`. Один и тот же сервер обслуживает собственное окно мастера и подключённых игроков, а права зависят от того, кто прислал запрос.

### Каталог

| Метод и путь | Что делает |
| --- | --- |
| `GET /api/catalog/categories` | Категории и количество объектов |
| `GET /api/catalog/:category?q=&page=&pageSize=&<фильтры>` | Список с поиском, фильтрами и страницами |
| `GET /api/catalog/:category/facets` | Возможные значения фильтров |
| `GET /api/catalog/entity/:id` | Карточка объекта, текущая ревизия |
| `GET /api/catalog/entity/:id/revisions/:rev` | Конкретная ревизия |
| `GET /api/health` | Версии программы, протокола и каталога |

### Персонажи (этап 4)

`GET/POST /api/characters`, `GET/PATCH /api/characters/:id`, `POST /api/characters/:id/preview` (расчёт листа без сохранения), `POST /api/characters/:id/level-up` (тот же механизм используется при создании персонажа N-го уровня, Р36), `POST /api/characters/:id/finalize`, `GET/PUT /api/characters/:id/portrait`.

### Игра (этапы 5–7)

Вход в кампанию, команды (`POST /api/campaigns/:id/commands`) и WebSocket `/api/campaigns/:id/live` с уведомлениями о подтверждённых изменениях. Контракт команд — по ТЗ, раздел 18.

Общие правила:

- Каждый запрос проверяется схемой Zod; неверный запрос получает ответ `400` с понятным текстом.
- Единый формат ошибки: `{ "error": { "code": "not_found", "message": "Заклинание не найдено" } }`.
- Списки постраничные: `{ "items": [...], "total": 524, "page": 1, "pageSize": 50 }`.
- Фильтрация и сортировка выполняются в SQL.

## 8. Интерфейс

### 8.1. Функционал (Figma) и дизайн — разные вещи

Интерфейс складывается из двух слоёв:

| Слой | Что отвечает | Откуда берётся |
| --- | --- | --- |
| **Функционал** | Какие экраны есть, какие данные на них видны, какие кнопки и выборы, порядок шагов, переходы | Макеты Figma (Р27) + ТЗ |
| **Визуальный дизайн** | Цвета, шрифты, форма кнопок и карточек, иконки, фон, анимации, раскладка в деталях | Этапы Д1–Д3 (Р28) |

Состояние макетов Figma:

- **Готово:** экраны до создания персонажа включительно.
- **Не начато:** создание кампании, редактирование NPC, создание хоумбрю (предметы, NPC), игровая комната мастера, игровая комната игрока.

Правила:

- Расположение элементов в Figma — подсказка, а не требование. Если дизайн на этапе Д1–Д3 предложит другую раскладку с тем же функционалом, это нормально.
- Цвета и шрифты Figma не переносятся в код автоматически.
- Перед этапом 4 ассистент сверяет макеты с ТЗ и правилами создания персонажа по чек-листу 8.3 и пишет список пропусков в `design/figma-review.md`. Что дорисовать, решает автор.
- Экраны, которых нет в Figma, сначала получают функциональную схему (этап Д2) и только потом программируются.
- Визуальные решения оформляются как дизайн-токены (`packages/ui/tokens`) и набор базовых компонентов. Экраны используют только их, без «магических» цветов в коде.

### 8.1.1. Этапы дизайна

| Этап | Результат | Как делается |
| --- | --- | --- |
| **Д1. Концепция и дизайн-система** | 2–3 варианта настроения (тёмное фэнтези, пергамент, «как в BG3» и т.п.) → выбранный вариант → палитра, шрифты, сетка, базовые компоненты (кнопка, поле, вкладка, карточка, подсказка, ячейка инвентаря, слот куклы), источник иконок | Чат «Дизайн» делает варианты: в Figma через коннектор или как HTML-прототипы, которые можно открыть и посмотреть. Автор выбирает и правит |
| **Д2. Функциональные схемы недостающих экранов** | Схемы (без стиля) для кампании, NPC, хоумбрю, комнат мастера и игрока | Автор в Figma, как уже сделано для создания персонажа, или ассистент по ТЗ, затем правки автора |
| **Д3. Дизайн игровых экранов** | Экраны из Д2 в стиле Д1 | Чат «Дизайн», приёмка автором |

Шрифт Ruslan Display из v0.1 и тёмная тема — только кандидаты для Д1, а не принятый стиль.

### 8.2. Что берём у BG3 (Р23)

| Область | Как в BG3 | Чьи правила |
| --- | --- | --- |
| Создание персонажа | Пошаговые вкладки: раса → подраса → класс → подкласс → предыстория → характеристики → навыки → заклинания → внешность → итог. Справа всегда видна сводка и подсказки | 5e 2014: доступные выборы, закуп очков, бонусы расы |
| Подсказки | При наведении на число — разбор: «КД 16 = 10 + кольчуга… + щит 2» | Расчёт из движка правил, каждое слагаемое со ссылкой на источник |
| Инвентарь | Сетка ячеек с иконками, вес и деньги внизу, сортировка и фильтры, контейнеры | Вес и цены — 5e 2014; перегруз — по правилам 5e (вариант с порогами — опция кампании) |
| Кукла | Персонаж со слотами: голова, плащ, доспех, перчатки, обувь, амулет, 2 кольца, ближнее оружие (основная и вторая рука), дальнее оружие | Ограничения 5e: руки, владение доспехами, настройка до 3 магических предметов |
| Карточка предмета или заклинания | Крупная карточка: название, тип, ключевые числа вверху, описание ниже, источник | Данные каталога |
| Лист персонажа | Характеристики, спасброски, навыки, КД, хиты, скорость, инициатива, особенности, ресурсы | 5e 2014 |

Правила BG3, которых нет в 5e 2014 (зелье бонусным действием, преимущество с высоты, особые заклинания и черты BG3), не применяются. Если такие правила понадобятся, их можно добавить как хоумбрю-правила кампании.

### 8.3. Сверка макетов

Чек-лист, по которому проверяются функциональные макеты каждого экрана:

- все шаги и выборы из ТЗ (раздел 6) и правил создания персонажа присутствуют;
- состояния: пусто, загрузка, ошибка, недоступный выбор (с объяснением почему), неполные данные;
- что видно мастеру и что игроку;
- поведение при смене расы или класса (ТЗ: пересчёт без «хвостов»);
- размеры окна: минимум 1366×768, ориентир 1920×1080;
- клавиатура и фокус;
- длинные русские названия и описания.

### 8.4. Общие правила

- Одно приложение с роутером; экраны открываются из главного меню (Р33): Подключиться к игре · Мои персонажи · Мои кампании · Справочник · Хоумбрю · Настройки · Выход.
- Запросы к серверу — только через TanStack Query и общий клиент из `packages/shared`.
- Весь интерфейс на русском, оригинальные названия показываются рядом.

## 9. Правила качества

### Код

- Читаемость важнее краткости. Не писать маршрут, схему и обработку ошибок одной строкой.
- Никаких веток по названию объекта (`if (name === "Эльф")`). Механика задаётся данными.
- Неизвестное значение остаётся неизвестным (`null` и пометка), а не подменяется нулём.
- Каждый новый расчёт правил — с тестом и контрольным примером из [правил создания персонажа](../character-creation-rules-engine.md).

### Проверки

- `npm run check` = lint + typecheck + тесты. Проходит перед каждым коммитом и в CI.
- Тесты парсеров — на сохранённых страницах; тесты сервера — на временных базах; сценарии в собранной программе — Playwright.
- Перед релизом: zip запускается на чистой Windows-машине (или в песочнице Windows) без установленного Node.js; данные появляются только в `data/`.

### Git

- Небольшие коммиты с понятными сообщениями. Не копить незакоммиченную работу.
- В git не попадают: базы, кэш, бэкапы, книги, `.env`, собранные программы.

### Работа с ИИ-ассистентом

- Перед крупным этапом ассистент пишет короткий план и согласует его.
- Ассистент не объявляет этап «выполненным» без проверки. Статус «принято» ставит только автор проекта.
- Если ассистент сомневается в правиле D&D, в макете или в желаемом поведении — спрашивает, а не угадывает.
- Решения, меняющие архитектуру, записываются в раздел 2.

## 10. Разработка и запуск

- Нужны Windows 10/11 x64 и Node.js 24 LTS (только разработчику; пользователю программы Node.js не нужен).
- Команды разработчика (план):

  ```
  npm ci
  npm run catalog:fetch        # докачать недостающие страницы DnD.su
  npm run catalog:build        # собрать catalog.db из кэша (--fixtures — тестовый, --strict, --fresh, --force)
  npm run catalog:compare-legacy  # сверка каталога с v0.1
  npm run dev                  # Electron с горячей перезагрузкой интерфейса
  npm run check                # lint + typecheck + тесты
  npm run dist                 # собрать zip портативной программы
  ```

- В режиме разработки папка `data/` лежит в `storage/dev-data/`, чтобы не смешивать её с собранной программой.
- **Диск C — по минимуму (решение автора, 2026-10-27).** Всё, что нужно установить, ставится в `D:\programm\`. Кэши перенаправляются переменными среды пользователя: `npm_config_cache=D:\programm\npm-cache`, `ELECTRON_CACHE=D:\programm\electron-cache`, `ELECTRON_BUILDER_CACHE=D:\programm\electron-builder-cache`, `PLAYWRIGHT_BROWSERS_PATH=D:\programm\ms-playwright`.

Этапы 7 и 8 поменялись местами относительно рубежей ТЗ (там C идёт перед D): для десктопной программы сеть — основа игры, а окончательную полировку разумнее делать, когда весь путь уже работает. Каркас сети закладывается с этапа 0 (сервер встроен сразу), поэтому этап 7 не означает переделки.

### Этап 0 подробно

1. Закоммитить всю незакоммиченную работу v0.1.
2. Создать ветку и тег `legacy` на этом коммите, отправить их на GitHub.
3. В `main` убрать старый код (он остаётся в `legacy`), оставить `docs/`; документы v0.1, кроме ТЗ и правил создания персонажа, перенести в `docs/archive/v0.1/` (Р42).
4. Каркас монорепозитория (раздел 4.3), ESLint, Prettier, Vitest, `tsc`.
5. Electron с изолированным окном, встроенный Fastify с `/api/health`, перенастройка путей на `data/`.
6. electron-builder: сборка zip; проверка запуска без установки.

## 13. Организация работы по чатам (Р29)

### 13.1. Почему так

Автор проекта предложила два варианта: (1) каждый этап — в отдельном чате с инструкциями от главного чата или от чата прошлого этапа; (2) у каждого чата своя функция: дизайн, защита, архитектура, тестирование и т.д.

Принято их сочетание:

- **Основа — вариант 1, но с главным чатом в центре.** Одна функция (например, «инвентарь») затрагивает сразу базу, сервер, интерфейс и тесты. Если разнести её по чатам-«отделам», каждый будет знать только свой кусок, понадобится много передач, и чаты начнут править одни и те же файлы. Чат этапа делает функцию целиком.
- **Вариант 2 — для проверок и дизайна.** Профильному чату полезно смотреть «свежим взглядом» и со своим чек-листом. Поэтому дизайн, ревью безопасности, тестирование и ревью архитектуры — отдельные чаты, которые подключаются под задачу, а не живут постоянно.
- **Цепочка «чат прошлого этапа → следующий» не используется как единственный способ передачи.** Через несколько этапов решения теряются, как в испорченном телефоне. Бриф каждому этапу выдаёт главный чат, сверяясь с этим документом.

### 13.2. Роли чатов

| Чат | Что делает | Что не делает |
| --- | --- | --- |
| **Главный (координатор)** | Ведёт этот документ, план, решения (раздел 2) и открытые вопросы; пишет брифы этапов; принимает отчёты; запускает профильные проверки | Не пишет код этапов |
| **Этап N** | Реализует этап по брифу: код, тесты, документация модуля. Работает в своей ветке, заканчивает пулл-реквестом и отчётом | Не меняет решения раздела 2 сам: предлагает их в отчёте |
| **Дизайн** | Этапы Д1–Д3: концепции, дизайн-система, экраны; сверка макетов по чек-листу 8.3 | Не программирует экраны |
| **Безопасность** | Ревью перед этапом 7 и перед каждым релизом: сеть, сессии, права, Electron | Не чинит сам: пишет список проблем |
| **Тестирование** | Проверяет готовый этап по сценариям ТЗ, пишет недостающие сценарные тесты | Не принимает этап за автора |
| **Архитектура** | Ревью при крупных изменениях структуры (новый пакет, смена библиотеки, схема базы) | — |

### 13.3. Как передаётся информация

Чаты не видят друг друга. Всё, что должен знать следующий чат, лежит в репозитории:

```
docs/v2/
├─ technical-documentation.md     этот документ
└─ handoff/
   ├─ coordinator.md             передача между главными чатами: где мы, что дальше
   ├─ stage-01-brief.md          бриф этапа от главного чата
   ├─ stage-01-report.md         отчёт чата этапа
   ├─ review-security-01.md      отчёты профильных чатов
   └─ templates/                 шаблоны брифа и отчёта
```

**Бриф** (пишет главный чат): цель этапа; что входит и что не входит; ссылки на разделы ТЗ, этого документа и макеты Figma; критерии «готово»; известные риски; вопросы, которые нельзя решать без автора.

**Отчёт** (пишет чат этапа): что сделано; как проверено (команды, сценарии, результаты); что не сделано или не проверено; предложенные решения для раздела 2; новые открытые вопросы; что важно знать следующему этапу.

### 13.4. Порядок одного этапа

1. Главный чат пишет бриф и согласует его с автором.
2. Автор открывает новый чат этапа (или главный чат запускает его сам из Claude Code как отдельную сессию в своей ветке) с текстом: «Прочитай `docs/v2/technical-documentation.md` и `docs/v2/handoff/stage-NN-brief.md`, выполни этап».
3. Чат этапа работает, коммитит, открывает пулл-реквест, пишет отчёт.
4. При необходимости главный чат запускает профильную проверку (тестирование, безопасность).
5. Автор смотрит результат. Главный чат переносит принятые решения в раздел 2 и обновляет статус этапа.
6. Пулл-реквест сливается в `main` только после приёмки автором.

### 13.5. Правила для всех чатов

- Первым делом прочитать этот документ и свой бриф.
- Не ссылаться на «как обсуждали в другом чате»: если это важно, оно должно быть в файле.
- Два чата не правят одни и те же файлы одновременно. Параллельно работают только чаты с непересекающимися областями (например, «Дизайн Д1» и «Этап 2: снаряжение»).
- Чат, который упёрся в вопрос к автору, останавливается и спрашивает, а не угадывает.
- Общение с автором: отвечать кратко. Когда просишь автора что-то сделать самой (слить пулл-реквест, установить программу, нажать кнопку на GitHub) — объяснять как начинающему разработчику: пошагово, где нажать и что должно получиться.
- Диск C используется по минимуму. Программы, браузеры Playwright и кэши (npm, Electron, electron-builder) ставятся в `D:\programm\`, временные файлы проекта — в `storage/`. Если инструмент по умолчанию пишет в `%LOCALAPPDATA%`, `%APPDATA%` или `Program Files` — перенаправить (раздел 10) или спросить автора.
