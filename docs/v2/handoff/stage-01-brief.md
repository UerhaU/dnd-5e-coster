## Цель

Первая настоящая категория каталога: все заклинания D&D 5e 2014 с DnD.su в `catalog.db`, собранные воспроизводимо из кэша страниц, с поиском и карточкой в программе.

Этап проверяет на одной категории всю цепочку раздела 6 (кэш → разбор → нормализация → ручные исправления → проверка → сборка → отчёт) и модель данных раздела 5. Снаряжение, расы и остальное (этапы 2–3) потом добавляются по этому образцу.

## Порядок работы

Этап делится на две части, **каждая — в своём чате**. После части А — промежуточный отчёт `docs/v2/handoff/stage-01-report.md`.

- **Часть А — данные** (Issues #2–#7): схема и сборка `catalog.db`, импортёр, ручные исправления, сверка с v0.1.
- **Часть Б — программа** (Issues #8–#12): API, поиск, экраны, Playwright, выборка для автора.

## Входит в этап

Часть А:

- **`packages/db`**: Drizzle-схема `catalog.db` по разделу 5.2 — `sources`, `content_entities`, `content_revisions`, `entity_sources`, `spell_index`, `content_links`, справочники (`magic_schools`, `damage_types`, `abilities` и те, что нужны заклинаниям), `content_search`, `catalog_info`. Только то, что нужно заклинаниям; таблицы других категорий не создавать.
- **Схема Zod `spell/v1`** в `packages/shared` по примеру 5.5. Неизвестное значение — `null` с пометкой, а не ноль (раздел 9).
- **Импортёр `packages/importer`** (cheerio): разбор страниц из кэша, нормализация, наложение `data/reviewed/`, проверка, сборка, отчёт. Ошибка одной страницы не останавливает импорт. ID по Р11 (`spell:fireball`).
- **Кэш**: на диске уже есть страницы заклинаний — `storage/imports/cache/dndsu-pages/` (523 страницы `dnd.su/spells/…`) и `storage/spell-fill/` (529 файлов; v0.1 брала 524 заклинания с `5e14.dnd.su`). Сначала выяснить, какой кэш полный и актуальный, и записать в отчёт. Скачивать (`fetch`) только недостающее, 1–2 запроса в секунду.
- **Фильтр редакции (Р12)** и источники как на DnD.su; в каждой книге — одна строка `sources`, без дублей v0.1.
- **Ручные исправления из v0.1** → `data/reviewed/spells/`: 46 проверенных правил из `spell-reviewed-rules.mjs` и составы материалов из `spell-materials.mjs`, в формате v2 (JSON, проверяется Zod).
- **`rules_json`** заполняется только для проверенных правил (`review_status: rules_verified`). Автоматически выделенные механики v0.1 (частичные, непроверенные) в `rules_json` не переносить; у таких заклинаний `automation: display_only`.
- **Ссылки на ещё не существующие объекты.** Предметы (этап 2) и классы (этап 3) пока не в каталоге. Материалы хранятся текстом и структурой без `itemIds`; классы — кодами (`class:wizard`) в `spell_index` без проверки ссылки. Связи `content_links` к предметам и классам добавят этапы 2–3. Записать это в отчёт как долг.
- **`npm run catalog:build`**: собирает `catalog.db`. Повторный запуск на тех же данных не создаёт новых ревизий; изменившийся объект получает новую ревизию, старые не меняются (Р21).
- **Сверка с v0.1**: число заклинаний (ожидается 524), поля по каждому заклинанию против `full-catalog.json`; отчёт о расхождениях в `storage/` и сводка в отчёте этапа.
- **`catalog.db` в программе**: лежит в `resources/`, открывается только для чтения; путь — через модуль путей этапа 0.

Часть Б:

- **API** по разделу 7 «Каталог»: `categories`, список с `q`, фильтрами и страницами, `facets`, карточка, ревизия; `/api/health` добавляет версию каталога. Схемы запросов и ответов — Zod в `shared`, единый формат ошибки.
- **Поиск FTS5** по русскому и английскому названию и тексту; «ё = е»; регистр не важен; поиск по началу слова.
- **Интерфейс** на временной теме (Р14): дизайн-токены в `packages/ui`, React Router, TanStack Query, общий клиент API из `shared`. Главное меню по Р33, где работает только «Справочник», остальные пункты видны, но неактивны («появится позже»). Экран списка заклинаний: поиск, фильтры (уровень, школа, класс, источник, ритуал, концентрация), сортировка, страницы. Карточка: все поля `spell/v1`, источники, ссылка на DnD.su, статус проверки. Тексты DnD.su — только как текст, без вставки HTML (4.5). Иконок нет — заглушка по категории (Р13).
- **Playwright**: сценарий в собранной программе — открыть «Справочник», найти «Огненный шар» по запросу «огнен», открыть карточку, проверить уровень и школу.
- **Выборка для автора** (Issue #12): 30 заклинаний, подобранных на сложные случаи (ритуал, концентрация, реакция, несколько источников, материалы с ценой, «ё» в названии, особый доступ классов) — список и что в каждом проверить, файлом в `docs/v2/handoff/`.

## Известные риски

- Кэша DnD.su нет в git и в CI (Р47) — CI собирает тестовый каталог из `data/fixtures/`; fixtures — только несколько страниц для тестов, не весь каталог.
- Два кэша с разным числом страниц и разными адресами (`dnd.su` и `5e14.dnd.su`) — выбрать один, записать в отчёт, не смешивать.
- Страницы DnD.su неоднородны (варианты накладывания, условия реакции, особый доступ классов) — тесты на fixtures для каждого случая; неразобранное поле — `null` и строка в отчёте импорта, а не догадка.
- Логика v0.1 сложная (дерево материалов «всё вместе»/«один из», рост по ячейкам) — переносить данные, а не схему из 84 таблиц.
- `npm run dist` в рабочей папке может падать с `EBUSY` — обход в отчёте этапа 0.
- `gh` в Git Bash может не находиться — запускать из PowerShell.

## Спросить автора, а не решать самому

Решено автором 2026-10-27 (Р47): тексты DnD.su в git **не кладутся**. В CI zip собирается с маленьким тестовым каталогом из `data/fixtures/`; полный `catalog.db` собирается на компьютере автора. Публикация текстов — вопрос В12, до первого релиза.

Спрашивать:

- Если разбор страницы расходится с v0.1 и непонятно, кто прав, — спросить, а не выбирать.
