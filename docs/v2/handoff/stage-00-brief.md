## Цель

Сохранить всю работу v0.1 так, чтобы её ничего не задело, и начать v2 с чистого `main`: каркас монорепозитория, пустое окно Electron со встроенным сервером, проверки качества и CI, первая сборка портативного zip.

Смысл этапа — снять технические риски до начала работы с данными: портативность (всё пишется только в `data/`), изоляция окна, нативный модуль SQLite внутри собранной программы, сборка и CI на Windows. После этапа 0 каждый следующий этап только добавляет код в готовую структуру.

## Порядок работы

Этап делится на две части. **Каждую часть лучше делать в своём чате**: часть А короткая, но меняет GitHub; часть Б большая. После части А пишется промежуточный отчёт `docs/v2/handoff/stage-00-report.md`, часть Б его дополняет.

### Часть А. Сохранение v0.1 (шаги 1–3)

Сейчас рабочая папка на ветке `v2-docs`, в ней около 60 незакоммиченных файлов v0.1 (каталог рас, снаряжение, аудит каталога). Их нельзя потерять и нельзя закоммитить в `v2-docs`.

1. Создать ветку `legacy` от `main` (`git switch -c legacy main`). Незакоммиченные изменения переходят вместе с ней: `v2-docs` трогает только `docs/v2/` и `design/`, пересечений нет. Если git откажется переключаться — остановиться и спросить автора.
2. Перед коммитом показать автору список файлов и проверить: нет баз, кэша, книг, `.env`, `*.local.*`, собранных программ, файлов больше 10 МБ. Закоммитить всю работу v0.1 в `legacy`.
3. Поставить тег `legacy` на этот коммит.
4. **С согласия автора** отправить на GitHub ветку `legacy` и тег `legacy`. Проверить, что на GitHub они есть и совпадают с локальными.
5. Создать ветку `stage-00-setup` от `main` и слить в неё `v2-docs`.
6. В `stage-00-setup` удалить код v0.1 через `git rm` (он остаётся в `legacy`): `backend/`, `src/`, `prisma/`, `public/`, `database/`, `scripts/`, HTML-страницы, `.bat`, старые конфиги. Оставить `docs/` (что именно — см. вопрос к автору), `design/`, `README.md`, лицензию, `.gitignore`.

Удалять только отслеживаемые файлы через `git rm`. Папки на диске, которых нет в git, — `storage/` (кэш DnD.su нужен этапу 1, архив `storage/dnd.sqlite` по Р15), `book/`, `.codex-logs/` — **не трогать**. Старые `node_modules/` и `dist/` удалять, только показав автору, что удаляется.

### Часть Б. Каркас v2 (шаги 4–7 и 10), в той же ветке `stage-00-setup`

## Входит в этап

- Часть А целиком (выше).
- **Монорепозиторий** по разделу 4.3: npm workspaces, `apps/desktop`, `packages/ui`, `packages/server`, `packages/db`, `packages/shared`, `packages/rules`, `packages/importer`, папки `data/reviewed/`, `data/fixtures/`, `storage/` (не в git, кроме `.gitkeep`). Пакеты, которые пока не нужны (`db`, `rules`, `importer`), создаются заготовками: `package.json`, `index.ts`, один тест. Так структура закреплена с первого дня.
- **Проверки**: TypeScript strict, ESLint, Prettier, Vitest, `tsc --noEmit`. Команда `npm run check` = lint + typecheck + тесты.
- **Electron** через `electron-vite`: окно с `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, узкий preload, Content-Security-Policy. В окне — React-страница с названием программы и статусом сервера (ответ `/api/health`). Темы и стиля нет (Р14, Р28).
- **Встроенный Fastify** в главном процессе: маршрут `GET /api/health` (статус, версия программы, версия SQLite). Сервер слушает **только `127.0.0.1`**. Открытие наружу — этап 7.
- **Проверка SQLite**: `better-sqlite3` подключается в главном процессе, `/api/health` возвращает версию SQLite из базы в памяти. Ни `catalog.db`, ни `user.db`, ни Drizzle-схем пока нет. Это проверяет, что нативный модуль собирается под Electron и работает в zip. (Предложение главного чата, требует согласия автора.)
- **Портативные пути** (раздел 4.2): корень — папка рядом с exe; в режиме разработки — `storage/dev-data/`. До готовности приложения перенастроить `userData`, `sessionData`, `logs`, `crashDumps`, чтобы Electron ничего не клал в `AppData`. При первом запуске создаются `data/` и `data/logs/`. Если папка недоступна для записи — понятное сообщение и выход, а не запись в другое место. Определение путей — отдельный модуль с тестами.
- **electron-builder**: цель `zip`, Windows x64. Имя программы и иконка — по ответу на В10. Команда `npm run dist`.
- **GitHub Actions** на `windows-latest`: `npm ci`, `npm run check`, `npm run dist`, zip сохраняется как артефакт сборки. Срабатывает на push и пулл-реквест.
- **Задачи этапа 1**: составить список задач этапа 1 (по таблице раздела 11) в отчёте. Завести их в GitHub Issues — только с согласия автора (`gh` на компьютере не установлен, см. вопросы).
- **`README.md`** под v2: что это за программа, как запустить zip, команды разработчика из раздела 10, где лежит v0.1 (`legacy`).
- **`.gitignore`** под новую структуру: `node_modules/`, `out/`, `dist/`, `release/`, `storage/*` (кроме `.gitkeep`), `*.db`, `.env`, `*.local.*`.

## Известные риски

- Потеря незакоммиченной работы v0.1 — первым действием коммит в `legacy`; не использовать `git stash`, `git reset --hard`, `git checkout -- .`, `git clean`.
- `git clean -fdx` или удаление «лишних» папок сотрёт `storage/` (кэш DnD.su и архив v0.1) и `book/` — удалять только через `git rm`; папки вне git не трогать.
- Нативный `better-sqlite3` собран не под Electron, и zip падает при запуске — пересобирать под Electron (`electron-builder install-app-deps` или `@electron/rebuild`), проверять именно в zip.
- Electron успевает создать папку в `AppData` до перенастройки путей — менять пути в самом начале главного процесса, проверять списком папок до и после.
- Кириллица и пробелы в путях (папка проекта — `dnd web`, имя программы — «Костёр») ломают сборку или запуск — проверять в такой папке; если не работает — остановиться и спросить автора про латинское имя файла.
- Windows SmartScreen и антивирус ругаются на неподписанный exe — ожидаемо, написать об этом в `README.md`.
- Этап большой, контекст кончится — делить на части А и Б, промежуточный отчёт после каждой.
